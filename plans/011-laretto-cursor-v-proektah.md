# 011 — Проекты Laretto переезжают на Cursor

Семь проектов (`plm`, `hrportal`, `installation`, `platform`, `docroi`,
`reference`, `assemblage-point`) настроены под Claude Code: скиллы, хуки и
правила лежат в `.claude/`, контекст — в `CLAUDE.md`. Теперь в них работают из
Cursor, и каждый проект должен нести то же самое в `.cursor/` и `AGENTS.md`,
а старое — убрать, чтобы один скилл не читался дважды. Истории независимы
между собой, объединены одним переездом; порядок задан владельцем: сначала
`plm`, потом `hrportal`, затем остальные.

Общее для всех историй: скиллы приходят из библиотеки
`~/.cursor/project_skills`, записанные в проекте отступления сохраняются;
хуки регистрируются в `.cursor/hooks.json`; проектные разрешения уже
`permissions.json` домашнего каталога; `.claude/` и `CLAUDE.md` удаляются
(восстанавливаются из git при нужде); результат коммитится и пушится в
базовую ветку проекта.

## US-0001. plm: Cursor видит правила проекта и ничего не читает дважды — 3 SP

**Боль.** Я как разработчик PLM, открывающий репозиторий в Cursor, хочу,
чтобы агент с первого сообщения знал стек, границы фронта и бэка, запреты и
какие скиллы когда читать — сейчас всё это написано для другого инструмента в
`CLAUDE.md`, скиллы Cursor подхватывает из чужой папки, а правила про ветки и
подписи коммитов никто не проверяет, и агент коммитит с трейлером, который
автопуш потом не отправляет.

**Размер.** Пучок осей: C (текст — контекстный файл собирается из двух
источников: старого контекста и реальных настроек проекта) и A (механический
перенос 28 скиллов, где механика не проходит в пяти с расхождениями против
библиотеки). Эталоны — `references/stories/US-0065.md` (1 SP, 5.1 мин) на
уровне выше: источник втрое длиннее и разделён на две аудитории;
`references/stories/US-0066.md` (1 SP, 4.8 мин) — перенос такой же
механический, исключений пять. Сумма времён с учётом общего контекста — полка
3 SP.

**Порядок и зависимости.** Независима; первая по решению владельца.

**Критерии приёмки.**

- В новом чате Cursor в корне проекта в перечне скиллов каждый проектный
  скилл встречается один раз, и это копия из `.cursor/skills`.
- Отступления, записанные в проектных копиях скиллов, не потеряны.
- Контекстный файл отвечает на «что это за проект, где границы, что
  запрещено, когда читать какой скилл» без обращения к истории чата.
- Попытка закоммитить с запрещённым трейлером или запушить в общую ветку
  останавливается хуком, а не замечается постфактум.
- Узкое горлышко: репозиторий открыт во второй сессии параллельно — работа
  не должна оставлять дерево на чужой ветке.

**Порядок демонстрации.**

1. Открываем проект в новом чате Cursor — перечень скиллов без дублей,
   контекст загружен.
2. Просим агента рассказать стек и запреты — ответ совпадает с
   контекстным файлом.
3. Валидатор библиотеки по `.cursor/skills` — чисто.
4. История git: один коммит с переездом в базовой ветке, ветка на удалённом
   сервере обновлена.

### Особенности реализации

Текущая копия `process-git/commits.md` отстаёт от библиотеки на 74 строки,
копия ничего своего не содержит — берётся библиотечная. У `frontend-ui`,
`docs-context-files`, `quality-review`, `quality-automated-enforcement`
расхождения двусторонние — сливать руками с сохранением секции отступлений.

**Боль.** Я как разработчик кадрового портала, у которого Cursor открыт

из них два собственных, которых нет в библиотеке и которые нужно перенести

**Порядок и зависимости.** После US-0001.

**Критерии приёмки.**

- Собственные скиллы проекта (`portal-checks`, `portal-deploy`) остались и
  читаются из `.cursor/skills` наравне с библиотечными.
- Общие ветки `main` и `develop` защищены хуком от прямого push.
- Остальные критерии — как в US-0001.

**Порядок демонстрации.**

1. Новый чат в корне проекта — перечень скиллов без дублей, собственные на

2. Пробный `git push origin develop` из агента — хук останавливает.

## US-0007. assemblage-point: Cursor видит правила проекта на языке новой библиотеки — 5 SP

**Боль.** Я как разработчик assemblage-point, работающий в домашней ветке,
хочу, чтобы Cursor читал правила проекта в том же составе, что и остальные

другое деление), и для каждого надо решить, в какой из новых он входит и что
из его отступлений сохранить; контекст 20 КБ — для другого инструмента.

**Размер.** Ось C и ось A, где у оси A исключений не пять, а пятьдесят:
каждый старый скилл надо сопоставить с новым, и механика проходит не везде.
Мест шесть: контекст, таблица соответствия, отступления старых скиллов,
слияние, раскладка фронта, ветка владельца. Эталоны —
`references/stories/US-0065.md`, `references/stories/US-0066.md`; против
US-0001 мест вдвое больше — полка 5 SP.

**Порядок и зависимости.** После US-0006; последняя — самая рискованная.

**Критерии приёмки.**

- Каждое отступление из старых скиллов либо попало в соответствующий новый
  скилл, либо названо в контексте как решение проекта.
- Работа ведётся от текущей рабочей ветки владельца, без переключения
  дерева на другую.
- Остальные критерии — как в US-0001.

**Порядок демонстрации.**

1. Таблица соответствия старое→новое показана целиком; потерь отступлений нет.
2. Новый чат — скиллы без дублей, в составе новой библиотеки.
3. Валидатор чисто; коммит в текущей ветке на сервере.
