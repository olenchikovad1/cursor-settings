# Репозиторий установки: единая выкатка без сабмодулей

## Суть

Сабмодули не делаем. С проектами работаем как раньше: каждый проект — отдельный
репозиторий, отдельный клон у себя, отдельная сессия.

Рядом заводим **один маленький репозиторий установки** (`installation`). Кода
приложений в нём нет. В нём записано:

- **что ставим** — список единиц: платформа, общие сервисы, приложения;
- **откуда брать** — адрес git-репозитория каждой единицы;
- **с какой ветки** — какая ветка идёт в бой (например `main`);
- **куда ставить** — на какую машину и в какой каталог;
- **как выкатывать** — сама выкатка и каскад;
- **что сейчас стоит** — журнал выкаток: коммит и версии пакетов по каждой единице.

## Устройство

```
installation/
  installation.toml     состав: единица → репозиторий, ветка, машина
  deploy/               выкатка, каскад, локальный стенд
  deployed/             что где стоит; коммитится выкаткой сама
```

```toml
[machines.hub]
ssh = "hub"                      # имя из справочника SSH, адресов здесь нет
root = "/opt/platform-apps"

[[units]]
code = "platform"
repo = "https://github.com/olenchikovad1/platform.git"
branch = "main"
machine = "hub"

[[units]]
code = "reference"
repo = "https://github.com/olenchikovad1/reference.git"
branch = "master"
machine = "hub"
```

Список единиц не кладётся в платформу: подключение приложения не должно
требовать правки платформы (И-2).

## Откуда выкатка берёт код

Не из папки разработчика, а из git. Выкатка клонирует репозиторий в свой
служебный каталог, переключается на указанную ветку и собирает оттуда.

- **пути на машинах не важны** — нужен только адрес репозитория;
- **в бой попадает только запушенное** — незакоммиченная правка туда не доедет.
  Сейчас платформа собирается из рабочей копии, и такая правка может уехать под
  тегом коммита, в котором её нет.

## Контракт выкатки

Выкатка не знает, что внутри единицы. Каждый репозиторий отдаёт четыре вещи:

1. команду сборки образов;
2. команду прогона своих тестов;
3. боевое описание служб (compose-файл лежит **в репозитории самой единицы**);
4. адрес проверки готовности.

Платформа это уже умеет (`build.sh`, `ship.sh`, `apply.sh`, `/readyz`).
Приложения приводятся к тому же.

## Как понимает, что пора выкатывать

По каждой единице в `deployed/` записаны коммит и версии пакетов платформы,
из которых собрана текущая версия. Выкатывать нужно, если:

- в боевой ветке появился коммит новее записанного, или
- платформа опубликовала новые версии пакетов, от которых единица зависит.

Если ни то, ни другое не изменилось, единица пропускается.

## Каскад

Выкатили платформу — дальше по приложениям **по одному**:

1. проверить, изменились ли коммит или пакеты; нет — пропустить;
2. собрать новый образ из чистого клона;
3. прогнать тесты; упали — в бою остаётся старая версия, в отчёте причина;
4. поднять новую версию и дождаться готовности; не дождались — вернуть
   предыдущий образ;
5. записать результат в `deployed/` и закоммитить.

Цена: несколько секунд недоступности на приложение при подмене контейнера.

Порядок: платформа → общие сервисы → приложения. Кто кого читает, выкатка
берёт из манифеста приложения (потребляемые сервисы).

## Кто запускает

Коммит сам ничего не выкатывает. Варианты:

- **команда выкатки** — запускает человек или сессия. С неё начинаем;
- **автоматический запуск на пуш в боевую ветку** — GitHub Actions или опросчик
  на hub. Включаем, когда каскад пару раз отработает без сюрпризов.

## Локальный стенд

Одна команда поднимает всё по списку. Здесь нужны **ваши** клоны (чтобы видеть
незакоммиченное): выкатка находит их по адресу репозитория в корнях поиска и
запоминает пути в машинном файле, который не попадает в git.

## Новый сервис

Новая запись в `installation.toml`. Базу и пользователя ему заводит установка
(одна СУБД на машину, база и пользователь на владельца данных — решение 0007).
Приложение, которое его читает, объявляет это в своём манифесте.

## Порядок, если делать

1. Репозиторий установки и выкатка одной единицы из git; первая — платформа.
2. Контракт выкатки в приложениях, начиная с `reference`.
3. Каскад по изменившимся пакетам.
4. Первый общий сервис.
5. Общая СУБД на машину.
