# Границы транзакции

## Один вопрос решает почти всё

**Где происходит `commit` и кто им владеет.**

Если коммитит и сервис, и репозиторий — операцию уже нельзя откатить целиком.
Половина работы зафиксирована, вторая упала, и система осталась в состоянии,
которого по бизнес-смыслу не бывает.

## Правило

**Транзакцией владеет тот, кто знает границы операции.** Обычно это сервисный
слой или обработчик запроса — тот, кто понимает, что «оформить заказ» это одна
вещь, а не четыре.

Репозиторий делает `flush`, если нужно получить идентификатор, но **не
коммитит**. Он не знает, чем занят вызывающий и не окажется ли его работа частью
чего-то большего.

## Следствие для тестов

В тестах, работающих с реальной базой, `commit` подменяется на `flush`, а
транзакция откатывается после теста.

Без этого тестовые данные остаются в базе навсегда: следующий прогон видит чужие
строки, тесты начинают зависеть от порядка, а потом кто-то удивляется, откуда в
базе разработчика заказы из прошлого месяца.

Подмена делается **на уровне файла или фикстуры**, а не по желанию в каждом
тесте: правило, которое надо не забыть, забудут.

## Долгие транзакции

Транзакция, внутри которой идёт вызов наружу или ожидание пользователя, держит
блокировки всё это время. Правило простое: **внутри транзакции не ждут ничего,
чем не управляют.**

Нужно и сохранить, и вызвать внешний сервис — это два шага с явной точкой между
ними, а не одна транзакция.

## Что делать при частичном отказе

Если операция не может быть атомарной по существу — например часть данных живёт
во внешней системе — состояние после отказа описывается заранее. Не «такого не
случится», а «останется вот так, и вот как это исправляется».

## Признаки, что границы не проведены

- после ошибки в данных видна половина операции;
- тесты оставляют строки;
- откат «почему-то не откатывает»;
- в логах видны блокировки, которые ждут внешний сервис.

## Как выглядит

**Неправильно** — фиксирует репозиторий:

```python
class OrderRepo:
    def add(self, order: Order) -> None:
        self.session.add(order)
        self.session.commit()      # границ операции он не знает
```

Заказ сохранён, резерв склада — ещё нет. Упадёт следующий шаг — останется
половина операции, и откатывать её будет некому.

**Правильно** — фиксирует тот, кто знает границу:

```python
class OrderService:
    def place(self, cart: Cart) -> Order:
        order = self.orders.add(build_order(cart))
        self.stock.reserve(order)
        self.session.commit()      # одна операция — одна фиксация
        return order
```

## Проверка

- прервать операцию посередине — состояние откатилось целиком, без остатков;
- посмотреть, кто фиксирует изменения, — одно место, а не каждый слой;
- проверить, не уходит ли внутрь транзакции внешний вызов, — не уходит.

## Чего не делать

- фиксировать изменения из нескольких мест;
- держать транзакцию открытой на время внешнего вызова;
- полагаться на автоматическую фиксацию там, где операция составная.
