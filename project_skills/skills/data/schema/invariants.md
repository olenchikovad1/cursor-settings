# Инварианты в схеме

## Правило

**То, что должно выполняться всегда, выражается схемой, а не кодом.**

Проверка в коде — надежда, а не гарантия. Мимо кода данные попадают всегда:
через миграцию, через второй сервис, через ручной запрос при разборе инцидента,
через импорт. Схема — единственное место, мимо которого не пройти.

## Что кладётся в схему

**`nullable`.** Поле, которое обязано быть заполнено, объявляется обязательным.
«Мы всегда его заполняем» — не аргумент: однажды не заполнили.

**Уникальность по бизнес-смыслу** — ограничением. Проверка «сначала посмотрим,
нет ли такого» не работает при одновременных запросах: два процесса
одновременно ничего не находят и оба вставляют.

**Внешние ключи** — со стратегией удаления. Каскад, запрет или обнуление
выбираются осознанно: каскад, поставленный по умолчанию, однажды удалит больше,
чем ожидалось.

**Проверочные ограничения** для правил, выразимых на одной строке: неотрицательная
сумма, дата окончания не раньше даты начала, значение из списка.

## Индексы

На каждое поле, по которому идёт **поиск, фильтрация, сортировка или
соединение**.

Признак пропущенного индекса — запрос, который на тестовых данных мгновенный, а
на боевых заметен. Тестовые данные почти всегда меньше на порядки, поэтому
отсутствие индекса на них не проявляется вовсе.

Обратное тоже верно: индекс на поле, по которому никто не ищет, стоит места и
замедляет запись.

## Чего в схему не кладут

Правила, зависящие от нескольких строк или от внешнего состояния: «не более
трёх активных заказов на клиента», «нельзя отгрузить, пока не оплачено».
Их место — в домене, и там же называется точка проверки.

Инвариант без указания места проверки — пожелание, а не правило.

## Признаки, что правило живёт не там

- в базе есть строки, нарушающие то, что код «гарантирует»;
- одна и та же проверка написана в трёх местах, и они слегка разные;
- при импорте или миграции данные приходится чинить руками.

## Как выглядит

**Неправильно** — уникальность держится проверкой в коде:

```python
if await repo.get_by_email(email):
    raise EmailTaken()
await repo.add(User(email=email))
```

Два одновременных запроса пройдут проверку оба. Дубль появится там, где его
«не может быть», и обнаружится через месяц в отчёте.

**Правильно** — правило в схеме, код превращает нарушение в понятный отказ:

```python
# миграция
op.create_unique_constraint("uq_users_email", "users", ["email"])

# сервис
try:
    await repo.add(User(email=email))
except IntegrityError:
    raise EmailTaken()
```

## Проверка

- попробовать записать состояние, нарушающее правило, в обход приложения — база
  не даёт;
- посмотреть, какие правила держатся только кодом, — таких нет либо названо
  почему;
- проверить наличие индексов под запросы, которые действительно выполняются.

## Чего не делать

- держать обязательность и уникальность только в коде;
- откладывать внешние ключи до лучших времён;
- добавлять индексы наугад, не глядя на запросы.
