# Модели данных

Про отображение сущностей в ORM. Ограничения и индексы — в
[invariants.md](invariants.md), здесь они не повторяются.

## Связи объявляются явно

У каждой связи — `relationship()` с `back_populates` с обеих сторон. Связь,
объявленная в одну сторону, работает, пока кто-нибудь не пойдёт с другой.

Внешний ключ и поведение при удалении согласованы: то, что написано в
`ondelete` на уровне базы, и то, что делает `cascade` на уровне ORM, должны
означать одно и то же. Расхождение проявляется в момент удаления, когда база и
код действуют по-разному.

Каскад выбирается осознанно. `cascade="all, delete-orphan"` уместен для
подчинённых сущностей, у которых нет жизни без родителя (позиции документа), и
опасен для справочных.

## Стратегия загрузки — часть модели

**Ленивая загрузка по умолчанию — самая дорогая привычка в ORM.** Она даёт
запрос на каждое обращение к связи, и цикл по сотне записей превращается в сто
запросов. На тестовых данных это незаметно.

**В асинхронном режиме ленивой загрузки нет вовсе**: обращение к незагруженной
связи падает с `MissingGreenlet`. Загрузка задаётся явно в запросе:
`selectinload` для коллекций, `joinedload` для «многие к одному».

Приём, который окупается: поставить связям `lazy="raise"`. Тогда забытая
загрузка падает **сразу и в разработке**, а не под нагрузкой или в проде. Это
превращает «медленно» в «сломано», а сломанное чинится.

## Типы несут смысл

Родные типы базы использовать там, где они что-то означают: `UUID`, `JSONB`,
`ARRAY`, диапазоны дат, `numeric` для денег.

Деньги — **не** `float`. Округление в двоичной дробной арифметике даёт
расхождения в копейках, которые потом ищут неделями.

Время — в UTC и с зоной. Локальное время появляется только на границе
отображения. Хранение «наивного» времени однажды сдвинет всё на час.

Перечисления — либо родной тип базы, либо строка с проверочным ограничением.
Число вместо перечисления делает данные нечитаемыми при разборе инцидента.

## Модель — только отображение

Бизнес-правила живут в сервисах. В модели остаётся: колонки, связи,
ограничения, простые производные свойства без обращения к базе.

Причина не в чистоте. Метод модели, который ходит в базу, делает это в момент
обращения к атрибуту — там, где вызывающий этого не ждёт. Отсюда лишние
запросы и падения в асинхронном коде.

## Повторяющееся выносится в примеси

`created_at` и `updated_at` со значениями на стороне базы, мягкое удаление,
идентификатор — то, что есть почти у всех сущностей, объявляется один раз.

Значения времени задаёт **база**, а не приложение: иначе метки зависят от часов
процесса, а при вставке из миграции их не будет вовсе.

## `__repr__` окупается

Короткое представление с ключом сущности. Без него в логах и на разборе видно
`<Order object at 0x7f...>`, и приходится лезть за идентификатором отдельно.

В `__repr__` не попадают персональные данные и секреты (см. `quality-security`).

## Схему создают миграции

`create_all` — только для тестов. В любом окружении, где данные переживают
перезапуск, схема появляется миграциями и никак иначе: `create_all` не умеет
изменять существующие таблицы и молча оставит схему прежней (см.
[migrations.md](migrations.md)).

## Признаки, что модель написана неудачно

- один запрос порождает десятки — не задана стратегия загрузки;
- обращение к связи падает в асинхронном коде;
- модель импортирует сервисы;
- в модели есть метод, который делает запрос;
- одно и то же поле объявлено в пяти моделях по-разному.

## Как выглядит

**Неправильно** — связь объявлена с одной стороны и со стратегией по умолчанию:

```python
class Order(Base):
    items = relationship("OrderItem")
```

Ленивая загрузка даст отдельный запрос на каждый заказ в списке, а в
асинхронном коде обращение к незагруженной связи просто упадёт.

**Правильно** — обе стороны названы, стратегия выбрана:

```python
class Order(Base):
    items = relationship("OrderItem", back_populates="order", lazy="selectin")


class OrderItem(Base):
    order = relationship("Order", back_populates="items")
```

## Проверка

- открыть модель и сказать, что она загрузит при обращении к связи, — ответ
  есть в объявлении;
- поискать в модели что-нибудь, кроме отображения, — нет;
- посмотреть типы полей — они выражают смысл, а не только форму хранения.

## Чего не делать

- полагаться на стратегию загрузки по умолчанию;
- держать в модели правила предметной области;
- описывать связь с одной стороны, когда нужны обе.
