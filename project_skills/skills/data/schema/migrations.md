# Миграции

## Что такое миграция

**Минимальное изменение, приводящее прежнее состояние базы к новому.**

Не слепок схемы. Не «привести всё в соответствие с моделями». Не изменение ради
изменения.

Автогенерация даёт черновик, а не результат: она не знает, что важно, а что
попало в дифф случайно. Сгенерированную ревизию читают и вычищают.

## Все ревизии одинаковы по форме

Файл ревизии — **всегда `.py`**. Не `.sql`, не смесь. Причина не в
единообразии ради единообразия: только питоновская ревизия участвует в цепочке
`down_revision`, умеет ветвиться, знает про диалект и может выполнять условную
логику при переносе данных. Сырой SQL внутри `op.execute()` допустим — как
часть ревизии, а не вместо неё.

**Накатываются только через Alembic.** Не руками в консоли базы, не отдельным
скриптом, не «я быстренько выполню на бою». Иначе состояние базы расходится с
таблицей версий, и следующая ревизия падает или, хуже, проходит на схеме,
которой не ожидала.

Шапка одинаковая у всех:

```python
"""краткое описание: что делает ревизия

Revision ID: 0007_pick_tasks
Revises: 0006_stock_documents
Create Date: 2026-09-05
"""

from collections.abc import Sequence

import sqlalchemy as sa
from alembic import op

revision: str = "0007_pick_tasks"
down_revision: str | None = "0006_stock_documents"
branch_labels: str | Sequence[str] | None = None
depends_on: str | Sequence[str] | None = None


def upgrade() -> None:
    ...


def downgrade() -> None:
    ...
```

Что здесь существенно:

- **идентификатор ревизии осмысленный**, а не случайный хеш: `0007_pick_tasks`
  читается в `git log`, в списке файлов и в таблице версий. Случайный хеш не
  говорит ни о порядке, ни о содержании;
- **номер с ведущими нулями** — файлы сортируются по порядку применения, и
  цепочка видна глазами;
- **описание в докстроке — что ревизия делает**, а не «миграция»;
- **типы у полей ревизии проставлены** — они попадают под проверку типов
  наравне с остальным кодом.

Отступление от шаблона допустимо только там, где Alembic требует иного
(ветвление через `branch_labels`), и с причиной в комментарии.

## Безопасность важнее краткости

Если одним шагом сделать безопасно нельзя — делается несколько.

Классический случай — перенос данных в другую структуру:

1. создать новое и перенести данные;
2. отдельной ревизией удалить старое.

Между ними есть **точка, в которой можно остановиться и откатиться, не потеряв
данные**. Это и есть смысл разделения, а не аккуратность ради аккуратности.

Тот же приём для несовместимых изменений столбца: добавить новый, заполнить,
переключить чтение, и только потом удалить старый.

## `downgrade` обязателен

Он возвращает базу в прежнее состояние. Не заглушка, не `pass`, не «вряд ли
понадобится».

Если откат в принципе невозможен — например данные уже уничтожены — это
называется в комментарии к ревизии, а сама операция выносится в отдельный шаг,
чтобы всё остальное осталось обратимым.

## Данные важнее косметики

Отдельная миграция ради комментариев к полям не нужна: она ничего не меняет для
данных и создаёт шум в истории.

Но если у столбца **меняется тип** — заодно приводится в порядок и его
комментарий, если тот разошёлся с реальностью. Ревизия уже трогает столбец,
второй раз к нему не возвращаются.

## Проверять на копии боевых данных

На пустой базе проходит почти любая миграция. Ломается она на существующих
строках: нарушенное ограничение, `NULL` там, где теперь нельзя, дубли при
добавлении уникального индекса, неконвертируемое значение.

Проверка на копии — часть работы, а не пожелание.

## Большие таблицы

Долгая блокировка останавливает сервис. Для больших таблиц это учитывается
заранее: индекс создаётся без блокировки, если СУБД умеет; заполнение делается
порциями; изменение типа разбивается на шаги.

Признак опасности — операция, переписывающая таблицу целиком.

## Порядок ревизий при параллельных ветках

Две ветки от одной ревизии займут одинаковые номера. Это чинится
перенумерованием одной из цепочек, а не ревизией-слиянием: слияние оставляет
историю, в которой нельзя разобраться.

Проверяется до мёрджа, а не после.

## Чек-лист перед мёрджем

- ревизия делает ровно то, что нужно задаче, без лишнего из автогенерации;
- `downgrade` написан и проверен;
- прогнано на копии боевых данных;
- если небезопасно одним шагом — разбито, и точка отката названа;
- номер не конфликтует с другими ветками.

## Проверка

- прогнать миграцию и откат на копии боевых данных — состояние совпадает с
  исходным;
- посмотреть, есть ли точка, на которой можно остановиться без потери данных, —
  есть;
- оценить время блокировки на объёме боевой таблицы, а не пустой.

## Чего не делать

- писать миграцию слепком схемы;
- удалять старое в той же миграции, где переносятся данные;
- проверять только на пустой базе;
- заводить отдельную миграцию ради косметики.
