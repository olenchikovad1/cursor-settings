# Эволюция контракта

## Признак, а не список примеров

Изменение **безопасно**, если клиент прошлой версии продолжает работать, не
зная о нём. **Ломающее** — если нет.

Список примеров устаревает и всегда неполон; признак работает всегда. Проверка
делается мысленно от лица самого старого живого клиента: что он пришлёт, что
получит, что с этим сделает.

Обычно безопасны: добавление необязательного поля в ответ, добавление
необязательного параметра, расширение диапазона принимаемых значений, новый
метод.

Обычно ломают: удаление или переименование поля, превращение необязательного в
обязательное, сужение принимаемых значений, изменение типа, изменение смысла
поля при том же имени — последнее хуже всего, потому что незаметно.

## Изменение смысла — самое дорогое

Поле осталось, тип остался, а означает оно теперь другое: `количество` было
штуками, стало упаковками. Ни один автоматический разбор этого не поймает,
клиент продолжит работать и будет молча ошибаться.

Правило: **смысл поля не меняется никогда**. Нужен другой смысл — нужно новое
поле и удаление старого по общей процедуре.

## Ломающее изменение: версия или срок

Два законных пути, и оба требуют явного решения.

**Версия.** Старая продолжает работать, новая живёт рядом. Обязательно
назначается, когда старая перестаёт поддерживаться, — иначе версий станет
пять, и поддерживать придётся все.

**Период совместимости.** Работают оба варианта одновременно, у периода есть
**названный срок окончания**. Период без срока не заканчивается: через год
никто не помнит, зачем в коде две ветки.

## Удаление поля — процесс, а не действие

Одномоментное удаление безопасным не бывает. Порядок:

1. поле помечается устаревшим — в описании контракта и в записях об изменениях;
2. клиентам сообщается, чем его заменить;
3. **появляется способ увидеть, пользуется ли им кто-нибудь** — счётчик
   обращений, запись в лог с кодом события (`ops-logging`);
4. поле удаляется, когда по этому счётчику видно, что им не пользуются, и
   срок вышел.

Третий шаг — тот, который пропускают, и именно он делает удаление безопасным.
Без него решение принимается на веру.

## Требования к клиенту тоже названы

Клиент обязан:

- **не падать от незнакомого поля** в ответе. Иначе сервер не сможет добавить
  ничего и никогда, и контракт замораживается навсегда;
- **переживать незнакомое значение перечисления** — как минимум не падать, а по
  возможности вести себя разумно;
- не полагаться на порядок элементов, если он не оговорён;
- не полагаться на текст сообщения об ошибке — только на код
  ([contracts.md](contracts.md)).

Это часть контракта, а не пожелание. Не записано — значит первое же расширение
сломает того, кто читал невнимательно.

## Внутренний и внешний потребитель — разные правила

**Внутренний** обновляется вместе с сервером, выкатывается тем же процессом,
известен поимённо. Для него ломающее изменение — согласованная работа, а не
процедура: договорились, поменяли обе стороны, выкатили вместе.

**Внешний** не обновится никогда: мобильное приложение прошлой версии останется
у пользователя, чужая интеграция написана людьми, которых не спросить. Для него
работает полная процедура без исключений.

Ошибка — применять правила внутреннего к внешнему, потому что «мы же
предупредили».

## Записи об изменениях ведутся вместе с изменением

Что поменялось между версиями, записывается **в момент правки**, а не
восстанавливается потом по истории коммитов. Восстановленное задним числом
всегда неполно: в историю попадает то, что меняли, а не то, что это означало
для клиента.

## Проверка

- добавить необязательное поле в ответ — клиент прошлой версии работает без
  изменений;
- прислать клиенту незнакомое значение перечисления — не падает;
- попробовать убрать поле — приходит путь из шагов, а не удаление;
- посмотреть, есть ли способ узнать, пользуется ли кто-то устаревшим полем, —
  есть;
- открыть записи об изменениях — по ним понятно, что клиенту делать.

## Чего не делать

- менять смысл существующего поля;
- удалять поле одним шагом, потому что «им никто не пользуется»;
- открывать период совместимости без срока окончания;
- считать предупреждение достаточным для внешнего клиента;
- восстанавливать список изменений задним числом.

## Смежное

- [contracts.md](contracts.md) — из чего контракт состоит и почему коды ошибок стабильны.
- `data-schema` — то же требование поэтапности, но для схемы данных.
- `ops-logging` — чем измеряется, пользуются полем или нет.
- `ops-release` — совместимость версий в момент выкатки.
