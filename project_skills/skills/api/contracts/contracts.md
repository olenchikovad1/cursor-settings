# Контракт метода

## Описывается целиком и до кода

Вход, выход, коды ошибок, поведение при пустом результате. Если контракт
достраивается по ходу, клиент подстраивается под фактическое поведение — и
дальше любая правка сервера ломает экран, про который никто не помнил.

## Пагинация и сортировка — часть контракта

Не деталь реализации. Список без описанной пагинации однажды вернёт десять тысяч
строк, и это заметит пользователь, а не разработчик.

Названо: чем ограничивается размер страницы, что происходит при выходе за
пределы, по каким полям возможна сортировка, какой порядок по умолчанию.

Порядок по умолчанию обязателен и должен быть детерминированным. Без явной
сортировки база вправе вернуть строки в любом порядке, и пагинация начинает
терять и дублировать записи между страницами.

## Ошибки: клиенту одно, в лог другое

**Клиенту** — что произошло и что с этим делать. Устойчивый код и понятное
сообщение.

**В лог** — чем именно вызвано: место, входные данные, состояние.

Смешение вредит в обе стороны. Подробности наружу рассказывают про устройство
системы тому, кому не следует. Отсутствие подробностей в логе делает разбор
невозможным.

## Коды ошибок стабильны

Их читают клиенты и на них строят поведение. **Переименование кода — ломающее
изменение**, такое же как удаление поля.

Отсюда: коды пишутся так, чтобы их не пришлось переименовывать — по смыслу
отказа, а не по месту в коде. `ORDER_ALREADY_SHIPPED` переживёт переезд функции,
`SHIPPING_SERVICE_ERROR_42` — нет.

## Пустой результат — не ошибка

Список, в котором ничего не нашлось, возвращает пустой список и успешный код.
Отсутствие запрошенного объекта по идентификатору — уже отказ.

Разница важна: клиент по-разному показывает «ничего не найдено» и «такого нет».

## Совместимость

Добавление необязательного поля совместимо. Всё остальное — нет: удаление поля,
ужесточение проверки, изменение типа, новый обязательный параметр.

Ужесточение особенно коварно: сервер начинает отвергать то, что раньше принимал,
и клиенты ломаются молча.

## Как выглядит

**Неправильно:**

```python
if not rows:
    raise HTTPException(404, "Ничего не найдено")
raise HTTPException(400, f"Нельзя отменить заказ в статусе {order.status}")
```

Пустой список объявлен ошибкой — клиент обязан отличать «нет данных» от «нет
такого ресурса». А отказ описан только текстом: клиенту, чтобы отличить его от
другого отказа, придётся сравнивать русскую фразу.

**Правильно:**

```python
return Page(items=rows, total=total, limit=limit, offset=offset)

raise DomainError(
    code="ORDER_ALREADY_SHIPPED",       # это читают клиенты, код стабилен
    message="Заказ уже отгружен",       # это читает человек
)
```

## Проверка

- взять метод и, не открывая тела, назвать по описанию контракта: что придёт,
  что вернётся, какие коды ошибок и что будет при пустом результате;
- запросить вторую страницу выборки — порядок устойчив;
- вызвать метод с заведомо неверным вводом — код ошибки тот же, что описан;
- сравнить коды ошибок с прошлым выпуском — не поменялись.

## Чего не делать

- описывать метод после того, как он написан, подгоняя контракт под код;
- возвращать разный вид ответа в зависимости от того, нашлось что-нибудь или нет;
- менять код ошибки, считая это мелочью;
- оставлять неопределённым поведение при пустом результате и при пагинации.
