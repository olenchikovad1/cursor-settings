# Коммиты

## Работа истории — отвечать на «почему»

Цель: посмотреть три-четыре последних коммита, задевающих место в коде, и
**однозначно понять, зачем оно такое** — и усомниться, не было ли решение
ошибочным.

Это и делает историю инструментом поиска ошибок. История, отвечающая только на
«что», для этого бесполезна: «что» видно из диффа.

## Заголовок

Тип и что сделано, коротко. `feat:`, `fix:`, `refactor:`, `docs:`, `test:`,
`chore:`.

## Тело — почему

**Чего в теле быть не должно:**

- прогоны тестов и их результат;
- количество тестов, файлов, строк;
- пересказ того, **как** сделано.

Ни одно из этого не отвечает на «почему» и занимает место, в котором должна быть
причина. Как сделано — видно в диффе, тесты — в CI.

**Признак настоящей причины: она называет, что было не так до изменения.**

- «сделал, потому что попросили» — отговорка;
- «список грузился целиком и на боевых данных отдавал десять тысяч строк» —
  причина.

Если изменение выбирает между вариантами, тело называет отвергнутый и почему.
Если решение крупное — ссылка на запись решения (`docs-decisions`).

## Служебных подписей нет

`Co-Authored-By` и подобные строки не пишутся. Они не несут информации для
читателя истории и занимают место в теле.

В Cursor такую подпись (`Co-authored-by: Cursor <cursoragent@cursor.com>`,
`Made with Cursor`) добавляет сам клиент, уже после того как команда написана, —
в тексте команды её не видно. Выключается это настройкой, а не старанием:
**Settings → Git & PRs → Attribution** (в старых версиях — Agent → Attribution).
Хук `guard_commit_trailers.py` отклоняет подпись, написанную в команде, а после
коммита проверяет `HEAD` и, если подпись появилась, говорит, что её убрать
(`git commit --amend`, пока коммит не отправлен). Список запрещённых подписей —
ключ `forbidden_trailers` в `rails.json`; проекту, где подпись Cursor нужна, —
`"allow_cursor_attribution": true`.

## Сообщение читается тем, у кого есть только репозиторий

Ссылка на то, что лежит вне репозитория и читателю недоступно, — потерянная
строка. «(план 048)», «см. задачу из сессии», «как обсуждали вчера» отправляют
его туда, куда он не попадёт, и занимают место, в котором должна была стоять
причина.

Проверка одна: **может ли читатель это открыть?** Номер задачи в трекере,
которым пользуется вся команда, — может, и он полезен. Номер плана из чужого
рабочего пространства, идентификатор сессии, «первое замечание владельца» — не
может, и для него это просто шум.

То же относится к кухне самой работы: сколько историй в плане, какой это круг
просмотра, чем мерили время, сколько прогонов понадобилось. Всё это живёт там,
где работу ведут. История репозитория переживёт и план, и пространство, в
котором он лежал, — а ссылка на них останется висеть.

**Неправильно:**

```text
merge: свёрнутое дерево онбординга и значок вкладки (план 048)
```

Через полгода «план 048» не открывается ничем. Читатель видит, что где-то есть
объяснение, и не может до него добраться.

**Правильно:**

```text
merge: онбординг открывается свёрнутым деревом, у вкладки есть значок
```

## Заголовок слияния называет, что появилось

Слияние — момент, когда изменение появляется в общей ветке, и его заголовок
читают, просматривая, что приехало в релиз. На этот вопрос не отвечают ни
«merge: ветка задачи» (не сказано ничего), ни ссылка на внутренний номер (см.
выше), ни пересказ того, из чего ветка состояла: её коммиты и так лежат прямо
под слиянием, и повторять их — значит писать дважды и расходиться при первой
же правке.

Тело слиянию обычно не нужно: причина каждого шага уже записана в его
коммите. Тело появляется там, где есть что сказать **о самом слиянии** —
принятое решение по смысловому конфликту, порядок выкатки, которого это
изменение требует, известное последствие для тех, кто обновится.

**Неправильно:**

```text
merge: значок вкладки платформы (план 049)

Добавлен значок, добавлена проверка на расхождение копий, поправлены типы.
Прогнано 524 теста, все зелёные.
```

Перечень изменений дублирует коммиты ветки, прогон тестов — дело CI, номер
плана не открывается.

**Правильно:**

```text
merge: у вкладки платформы и у экрана входа появился значок
```

## Единица коммита — завершённая логика, а не файл

Коммит из одного файла допустим, только если этот файл и есть вся логика.

**Не «один файл — один коммит». Одна завершённая логика — один коммит.**

Типичная зернистость: пользовательская история распадается на три-пять
логических изменений. Например:

1. модели данных и репозитории под фичу;
2. методы API и фронтенд под неё;
3. исправление всплывших по ней ошибок.

Дробить мельче не нужно: десять коммитов по файлу превращают историю в шум, и
искать в ней причину становится невозможно.

Дробить крупнее тоже не нужно: коммит, в котором смешаны новая функциональность
и рефакторинг, нельзя откатить по частям, и непонятно, что именно сломалось.

## Что делать, когда логика не завершена

Не коммитить полработы в общую ветку. Если нужно сохранить состояние — это
отдельная ветка или снапшот, а не коммит с сообщением «промежуточное».

## Как выглядит

**Неправильно:**

```text
fix: правки

- поправил api.py
- поправил models.py
```

Тело пересказывает то, что и так видно в изменениях, и не отвечает ни на один
вопрос того, кто откроет этот коммит через полгода.

**Правильно:**

```text
fix: бронь не зависает при отмене до подтверждения

Внешний сервис принимает отмену только после подтверждения брони: отмена,
ушедшая первой, возвращала 409, и бронь висела до истечения 15 минут.
Поэтому подтверждение теперь всегда предшествует отмене предыдущей.
```

## Проверка

`git log` по одному файлу или методу за последние несколько изменений. По телам
восстанавливается, зачем он менялся, **без чтения диффов**.

Не восстанавливается — тела написаны про «что», а не про «почему».

## Смежное

- [branches.md](branches.md) — где эти коммиты живут и куда вливаются.
- `docs-decisions` — куда выносится причина, если она длиннее абзаца.
- `docs-naming-and-comments` — та же задача внутри кода.
