# Продолжить с последнего места

Сценарий, под который это написано: в офисе вырубили свет или интернет, работа
продолжается дома. Или наоборот. Незакоммиченного не осталось нигде, кроме
диска той машины, — значит восстанавливать состояние надо по коммитам и
журналу плана.

**Работу не начинать.** Задача скилла — доложить состояние и спросить.
Пользователь мог уйти с середины намеренно, и решение «что дальше» — его.

## 1. Убедиться, что настройки свежие

`SessionStart`-хук уже сделал `git pull --rebase --autostash` в `~/.claude` и
разложил транскрипты с памятью. Проверить, что это правда сработало:

```bash
py -X utf8 ~/.claude/hooks/autosync_claude.py --status
py -X utf8 ~/.claude/hooks/sync_state.py --status
```

Если `не подтянуто` больше нуля или в логе видна ошибка пула — сказать об
этом **первым делом**: дальше всё будет читаться из устаревших файлов, и
любые выводы окажутся неверными.

## 2. Найти незакрытые планы

```bash
grep -l "^status: in-progress" ~/.claude/plans/[0-9][0-9][0-9]-*.md
```

Для каждого — прочитать frontmatter (`project`, `branch`, `base_branch`,
`remaining_sp`) и **хвост журнала**: последнюю запись `### <дата> · <ХОСТ>`.

Три вещи из журнала важнее всего:

- **Дальше** — что планировалось следующим шагом;
- **В работе на момент записи** — что было незакоммичено, когда всё
  прервалось. Именно это и потеряно, если запись сделана на другой машине;
- **Грабли** — чтобы не наступить второй раз.

Если последнюю запись писал **другой** хост (сравнить с `$COMPUTERNAME`) —
сказать это явно: «план 014 последним вёл OFFICE-PC, незакоммиченное оттуда
сюда не попало».

## 3. Сверить дерево проекта с планом

Путь — только через резолвер, вычислять нельзя:

```bash
py ~/.claude/hooks/resolve_project.py <project> --json
```

Дальше в этом каталоге:

```bash
git branch --show-current
git fetch --quiet
git log --oneline <base_branch>..<branch>
git status --short
```

**`git branch --show-current` обязателен и идёт первым.** Ворктри в схеме
нет: ветка задачи живёт в том же рабочем дереве, что и `base_branch`. Если
рабочая копия осталась на `develop`, а работа была в `task/...`, то сверка с
планом покажет, что не сделано ничего, — и это будет ложью. Не на той ветке
— переключиться (или сказать, если есть незакоммиченное, что мешает).

Затем сопоставить пункты плана с коммитами ветки и назвать:

- какие пункты закрыты (есть коммит и он делает то, что написано в пункте);
- какие не отражены в коммитах вообще;
- что лежит незакоммиченным прямо сейчас (`git status`).

Сверять по существу, а не по названиям коммитов: сообщение «feat: фаза 2» не
доказывает, что фаза 2 сделана. Смотреть диффы тех коммитов, в которых
сомнение.

## 4. Доложить и спросить

Коротко, по форме:

```
План 014, проект claude-home, ветка master.
Последняя запись журнала: 2026-09-02 · OFFICE-PC.
Закрыто: фазы 0, 1, 7.1 (6 SP). Остаток 33 SP ≈ 80 мин.
Не отражено в коммитах: 3.1 синк транскриптов, 6.2 скилл resume-work.
Незакоммичено сейчас: ничего.
Потеряно с офиса: правка alembic/0028 (по журналу была в работе).
Продолжать с 3.1?
```

Оценку остатка — через `calibrate.py estimate --sp ...` по нереализованным
пунктам, а не на глаз (см. `progress-time-estimates`).

## Если план не найден

Незакрытых планов нет — так и сказать, не выдумывать работу. Показать, что
менялось последним, чтобы пользователь сориентировался:

```bash
git -C ~/.claude log --oneline -10
```

## Проверка

- на второй машине попросить продолжить — приходит состояние: что закрыто, что
  в работе, чего нет в коммитах;
- сверить сказанное с деревом проекта — совпадает;
- посмотреть на последнюю строку ответа — это вопрос «продолжать с ...?», и
  `git status` после доклада показывает ровно то же, что до него.

## Чего не делать

- начинать работу до сверки состояния;
- полагаться на журнал, не глядя в дерево;
- считать незакоммиченное отсутствующим.

## Смежное

- `execute-plan` — собственно выполнение плана.
- `distributed-setup` — устройство синка, если что-то не подтянулось.
