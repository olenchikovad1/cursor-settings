# Слои первичны, домены — внутри слоя

## Что не работает

Буквально понятая предметная разбивка даёт корень такого вида:

```
orders/  warehouse/  catalog/  billing/  shipping/  returns/
pricing/ customers/  reports/  integrations/
common/  core/  shared/  utils/  config/
```

Десять доменных каталогов плюс пять общих. Внутри каждого домена повторяется
одна и та же структура, и дальше происходит предсказуемое:

- одинаковые по роли файлы лежат в десяти местах и **расходятся** — в одном
  домене схема валидирует, в другом нет;
- «общие» каталоги собирают всё, что не подошло ни одному домену, и
  превращаются в свалку;
- граница домена смещается — а вместе с ней приходится двигать пять файлов
  вместо одного.

Корень растёт вместе с числом доменов и перестаёт что-либо сообщать.

## Что работает

**Первично деление по слоям. Внутри слоя — файл на домен.**

```
models/       orders.py  warehouse.py  catalog.py  ...
schemas/      orders.py  warehouse.py  catalog.py  ...
repositories/ orders.py  warehouse.py  catalog.py  ...
services/     orders.py  warehouse.py  catalog.py  ...
api/          orders.py  warehouse.py  catalog.py  ...
```

Домены никуда не делись — они остались осью, просто вторичной. Внутри
`models/orders.py` лежат модели заказа и только они.

## Почему именно так

**Слоёв мало и их состав стабилен.** Модели, схемы, репозитории, сервисы, API —
этот набор не меняется годами. Доменов много, они появляются и их границы
двигаются. Изменчивое измерение не делают первичным: иначе структура проекта
переписывается вместе с предметной областью.

**Слой — это зона контроля данных, а не просто папка.** Каждый отвечает за своё
отношение к данным:

- **модели** — как данные хранятся и какие ограничения держит база;
- **схемы** — что принимается снаружи и что отдаётся наружу;
- **репозитории** — как данные достаются, без бизнес-смысла;
- **сервисы** — правила предметной области;
- **API** — контракт и права.

Деление по слоям поэтому не техническая условность: оно совпадает с ответом на
вопрос «кому что можно делать с данными». Разбивка по доменам этого ответа не
даёт — она говорит только «про что», но не «на каком основании».

**Одинаковое лежит рядом.** Все схемы видны в одном месте, и расхождение между
ними заметно сразу. Когда они разбросаны по доменам, расхождение обнаруживает
пользователь.

## Когда файл слоя становится большим

Файл превращается в каталог с тем же именем:

```
models/orders/__init__.py  order.py  order_line.py  status.py
```

Ось не меняется — меняется только глубина. Порог не в строках, а в том, что
файл стал сборником несвязанных вещей: заходишь за одной моделью и ищешь её
глазами.

## Домен наверх не поднимается

Такой необходимости не возникает. При явном делении на слои домен собирается
срезом: файл с его именем в каждом слое. Найти всё, что к нему относится, —
поиск по имени, а не обход дерева.

Это же снимает довод «а если понадобится вынести отдельно»: собрать срез по
слоям элементарно, и держать ради этого отдельную доменную иерархию не нужно.

## Общие каталоги

Их немного и у каждого назван предмет: конфигурация, работа с базой,
аутентификация, вспомогательные типы.

Каталог `utils` без предмета — то самое место, куда складывают всё
неопределившееся. Если он появился, полезно посмотреть, что внутри: обычно там
лежат две-три вещи, у каждой из которых есть законное место.

## В файле контекста

Раздел архитектуры описывает **оси, а не перечень папок**: что первично, что
вторично, где живёт слой и по какому признаку внутри него разложены домены.
Перечень каталогов устаревает первым (см. `docs-context-files`).

## Проверка

- назвать слой и домен для любого файла проекта — оба определяются однозначно;
- посмотреть, сколько мест надо открыть, чтобы понять один домен, — они
  предсказуемы и их немного;
- добавить новый домен — места для него уже определены.

## Чего не делать

- заводить каждому домену свой каталог верхнего уровня;
- держать в одном файле разные слои одного домена;
- называть слой по технологии, а не по роли.
