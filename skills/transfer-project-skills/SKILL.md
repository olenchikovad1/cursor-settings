# Перенос библиотеки правил в проект

Библиотека лежит в `~/.claude/projects_skills/` и **намеренно не
подхватывается**: её файлы не появляются в списке скиллов ни в одной сессии,
пока их не перенесли. Этот скилл — про то, как переносить.

## Что откуда берётся

```
projects_skills/skills/<область>/<имя>/SKILL.md    правило или индекс пакета
projects_skills/skills/<область>/<имя>/<лист>.md   листья пакета
projects_skills/hooks/<файл>.py                    хуки, подпирающие часть из них
projects_skills/transfer.py                        механическая часть переноса
```

В проекте всё ложится плоско: `.claude/skills/<область>-<имя>/SKILL.md`. Иначе
не работает — инструмент ищет скиллы ровно на один уровень глубже
`.claude/skills/`, и командой становится имя каталога.

**Пакет переносится целиком.** Часть правил библиотеки — это индекс и листья
рядом с ним (`write-skill`, лист `package.md`). Листья едут вместе с индексом и
только вместе с ним: у листа нет шапки, сам по себе он не подхватится никогда,
а индекс без листьев — оглавление без книги. Скрипт делает это сам; при ручном
копировании каталог копируется целиком, а не один `SKILL.md`.

Раздел отступлений дописывается только в индекс — иначе отступление придётся
искать по всему пакету.

## Порядок

**1. Показать план переноса.** Без `--apply` скрипт ничего не меняет:

```bash
py ~/.claude/projects_skills/transfer.py <путь к проекту>
```

Область целиком — `--area architecture` (ключ можно повторять). Область,
названная словами («перенеси архитектурные»), переводится в имя каталога.

**2. Задать вопросы одним списком — до переноса, а не после.** Спрашивается
только то, чего не видно по проекту:

- какие ветки считаются общими (посмотреть `git branch -r`, но подтвердить);
- какая команда считается прогоном, доказывающим работоспособность;
- нужны ли фронтендовые правила, если фронтенда в проекте не видно.

Вопросы задаются **разом**. Тридцать пять заготовок по вопросу на каждую —
это не перенос, а допрос.

**3. Решить, что не переносить.** Отказ — нормальный исход, а не недоработка.
Нет фронтенда — фронтендовые правила не ставятся. Пропущенное называется
списком с причиной.

Если пропущенное правило упоминается в перенесённых, скрипт это покажет:
ссылка в никуда хуже отсутствующей, потому что по ней идут.

**4. Перенести** тем же вызовом с `--apply`.

**5. Подключить хуки.** Скрипт кладёт файлы и печатает фрагмент для
`.claude/settings.json`. Фрагмент нужно **влить** в существующие настройки, а
не заменить их: там уже могут быть чужие хуки.

Лежащий, но не подключённый хук не делает ничего — и создаёт ложное ощущение,
что правило подпёрто.

**6. Настроить условия срабатывания.** Хуки не содержат зашитых имён веток и
команд, они читают `.claude/rails.json` проекта:

```json
{
  "shared_branches": ["main", "develop"],
  "proof_commands": ["make test"],
  "forbidden_trailers": ["Co-Authored-By"]
}
```

Настройка **заменяет** умолчание целиком, а не дополняет.

**7. Адаптировать под проект.** Механическая часть закончена, дальше — то,
чего скрипт не умеет: подставить настоящие команды проекта, его пути и его
конвенции вместо общих формулировок. Это и есть разница между «скопировал» и
«перенёс».

## Совпадение имён

**С проектными скиллами** — перенос останавливается, решение по каждому
принимает человек: затирать чужую работу молча нельзя.

**С личными скиллами** (`~/.claude/skills/`) — переносу не мешает и ошибкой не
является. Личный перекрывает проектный, то есть у владельца личной копии
работает она. Это норма: проектная копия существует для тех, у кого личной нет.

## Происхождение

В каждой копии остаётся `source` и добавляется `adapted` с датой. Дальше копия
и заготовка живут раздельно: правка библиотеки не чинит развёрнутые копии, и
наоборот.

## Отступление от правила в проекте

Если правило проекту подходит не целиком, оно **не режется**: отступление
записывается отдельно, с причиной. Как — в самом перенесённом правиле,
раздел про отступления.

## Проверка

- `.claude/skills/` проекта содержит столько каталогов, сколько правил
  переносилось, и имя каждого — `<область>-<имя>`;
- у каждого перенесённого пакета рядом с индексом лежат все его листья, и
  ссылки индекса на них открываются;
- ссылка на правило, которое не переносилось, помечена «(в библиотеке, сюда не
  переносилось)» — непомеченных ссылок в никуда нет. Сама помеченная ссылка
  нарушением не является: при переносе одной области это штатный исход;
- хуки прописаны в `settings.json`, а не просто лежат;
- нарушение подпёртого правила вызывает реакцию хука, настроенную под этот
  проект.

## Чего не делать

- переносить «на всякий случай» то, что проекту не подходит;
- заменять `settings.json` целиком вместо вливания;
- копировать руками один `SKILL.md` вместо каталога пакета;
- оставлять в перенесённых правилах общие формулировки там, где у проекта есть
  свои команды;
- подгонять проект под правило, вместо того чтобы записать отступление.

## Смежное

- `write-skill` — стандарт правил: состав, формат пакета, где чему место.
- `distributed-setup` — где лежит библиотека и как она синхронизируется между
  машинами.
