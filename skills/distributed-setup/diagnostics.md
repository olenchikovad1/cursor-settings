# Диагностика

## Что где НЕ лежит

| Данные | Где | Почему не в основной ветке |
|---|---|---|
| Транскрипты | ветка `transcripts` | 8–14 МБ на файл, история раздувала бы репозиторий |
| Замеры времени | ветка `calibration` | меняются каждый ход, забивали бы историю master |
| `local.json` | только локально | пути и роль машины разные; схема — в отслеживаемом `local.example.json` |
| `infra_ssh_hosts.md` | только локально, флешка | адреса и логины инфраструктуры |
| `sessions/`, `shell-snapshots/` | только локально | ключи сессий и мусор |
| `projects/` | только локально | кэш Claude Code, слаг зависит от пути |
| `.pending.json` | только локально | живёт минуты, конфликтовал бы зря |
| `logs/.rolling.json` | только локально | состояние катящегося коммита, sha у каждой машины свои |

## Диагностика

| Симптом | Что смотреть |
|---|---|
| план с другой машины не виден | `autosync_claude.py --status`, поле «не подтянуто» |
| `--resume` не показывает сессию | `sync_state.py --status`: есть ли файл в локальном слаге |
| путь не разрешается | `resolve_project.py --list --rescan`, корни в `local.json` |
| push не уходит | `logs/push.log` — там теперь весь вывод; затем `git push` руками |
| push отказал: `stale info` | лиза не сошлась, `origin/master` сдвинулся не нами: `git fetch origin master` и разбирать руками, коммит цел |
| ходы плодят коммиты вместо одного | `autosync_claude.py --status`, строка «катится»; если «свёртка выключена» — нет `rolling_commits` в манифесте |
| pull встал на конфликте | хук скажет и остановится; разбирать руками, он не полезет |
| требуют продолжать чужой план | `plan_session.py --status`: план заявлен другой сессией — так быть не должно, это баг хука, а не задание |
| хук молчит про план, который веду | заявки нет: `--claim <NNN> --session <UUID>`; проверить, что `cwd` внутри проекта плана |
| хук напомнил один раз и умолк | `logs/plan-guard.log`: «холостой цикл» — 30 ходов подряд без движения по плану, либо «потолок» |
| план закрыт, а заявка висит | `plan_session.py --release <NNN>` (шаг 4 `execute-plan`) |
| работа с другой машины не в `master` | так и задумано: `--show-wip <роль>`, дальше `--adopt-wip` или `--drop-wip --yes` |
| коммиты уходят в `master`, а не в `wip/*` | `machine.py --status` — роль не задана; либо нет `wip_branches` в манифесте |
| `master` на remote не двигается всю сессию | так и задумано: он публикуется на `SessionEnd` и на следующем `SessionStart` |
| чужая `wip/*` висит в докладе после слияния | `--adopt-wip` был не доведён до push: `logs/push.log`, затем `git push origin master` |
| правило игнора «не работает» | `git check-attr` и `git check-ignore --no-index` — **без `--no-index` git молча пропускает всё, что уже в индексе, и отвечает «правил нет»** |

## Проверка

- пройти по списку диагностики на живой поломке — он приводит к причине, а не
  к общим словам;
- проверить, что названные команды существуют и отвечают;
- после починки повторить проверку из соответствующего листа — зелено.

## Чего не делать

- чинить наугад, не посмотрев логи автосинка и push;
- считать проблему решённой, не повторив проверку;
- искать состояние там, где его нет по устройству схемы.
