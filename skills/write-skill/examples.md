# Примеры кода в правиле

## Зачем они нужны

Прозой образец не передаётся. Требование «тест проверяет поведение, а не
устройство» понятно ровно до того момента, когда надо написать первую строку, —
и там читатель воспроизводит то, что помнит, а помнит он чаще всего типовой
плохой пример.

Пара «неправильно / правильно» закрывает этот разрыв дешевле, чем три абзаца
объяснений, и остаётся в памяти дольше.

## Как оформляется

Порядок фиксированный: **сначала неправильно, потом правильно**, между ними —
строка о том, что именно сломается.

Так, а не наоборот: правильный вариант, прочитанный первым, выглядит
очевидным, и читатель не узнаёт в неправильном себя. Прочитанный вторым — он
воспринимается как ответ на уже показанную проблему.

````markdown
## Как выглядит

**Неправильно** — фиксирует репозиторий:

```python
class OrderRepo:
    def add(self, order: Order) -> None:
        self.session.add(order)
        self.session.commit()      # границ операции он не знает
```

Заказ сохранён, резерв склада — ещё нет. Упадёт следующий шаг — останется
половина операции, и откатывать её будет некому.

**Правильно** — фиксирует тот, кто знает границу:

```python
class OrderService:
    def place(self, cart: Cart) -> Order:
        order = self.orders.add(build_order(cart))
        self.stock.reserve(order)
        self.session.commit()      # одна операция — одна фиксация
        return order
```
````

Секция называется «Как выглядит» и стоит перед «Проверкой».

## Требования к самому примеру

- **Минимальный.** В примере остаётся только то, из-за чего он здесь. Лишние
  поля, обработка ошибок и логирование уводят взгляд с предмета.
- **Настоящий.** Вымышленных функций и несуществующих параметров быть не
  должно: их перепишут дословно. Если API точно не помнится — пример строится
  на том, что проверяемо, либо не пишется вовсе.
- **С последствием, а не с оценкой.** «Так неправильно» не объясняет ничего.
  «Два одновременных запроса пройдут проверку оба» объясняет всё.
- **Короткий комментарий внутри кода** ставится там, где без него неясно, на
  какую строку смотреть.

## Где примеров не бывает

Там, где требование не выразимо кодом: процесс, переписка, устройство
интерфейса, порядок разбора инцидента. Выдуманный пример там хуже отсутствия —
он сужает правило до одной ситуации, и его начинают применять буквально.

Тогда вместо кода работает признак нарушения: «две части системы делают одно и
то же по-разному», «после перезапуска состояние, по которому можно было понять
причину, исчезло».

## Язык примера

Тот, на котором пишется код, к которому правило применяется. Для правил
библиотеки это обычно Python на бэкенде и TypeScript на фронте. Комментарии
внутри примеров — русские, как и везде в коде
(`docs-naming-and-comments`).

## Проверка

- открыть пример и назвать, что сломается в неправильном варианте, — ответ в
  строке между блоками;
- убрать из примера любую строку — пример перестаёт показывать предмет
  (значит лишнего нет);
- проверить каждое имя в правильном варианте по документации — все
  существуют.

## Чего не делать

- ставить правильный вариант раньше неправильного;
- показывать различие без объяснения последствия;
- выдумывать API ради красоты примера;
- сочинять примеры к требованиям, которые кодом не выражаются.
