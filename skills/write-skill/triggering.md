# Описание и загрузка

## Описание в шапке решает, сработает ли правило

Его читает не человек, а механизм подхвата: по нему решается, загрузить правило
в этот разговор или нет. Поэтому оно пишется **под срабатывание**, а не под
красоту.

Устройство: что правило делает, и **когда его применять** — перечислением
ситуаций словами, которыми их описывают на практике. Не «правила работы с
базой», а «когда меняется схема, когда пишется миграция, когда падает
блокировка на большой таблице».

Слишком общее описание подхватывается везде и мешает. Слишком узкое не
подхватывается никогда. Проверяется просто: назвать три реальные ситуации, в
которых правило нужно, и посмотреть, следуют ли они из описания.

**Неправильно:**

```yaml
description: Use when implementing any feature or bugfix, before writing implementation code
```

Подхватится на правке документации, на переименовании файла и на разговоре о
планах — то есть там, где требования правила неприменимы, а место в контексте
оно займёт.

**Правильно:**

```yaml
description: Write the test first, make sure it fails for the right reason, then
  make it pass — and know where TDD does not apply. Use when implementing logic in
  backend or frontend code, when fixing a bug that should not return, and when
  deciding whether a change needs a test at all.
```

## Ссылка не загружает

`Смежное` — это заметка читателю, а не подключение. Соседнее правило по ссылке
само в контекст не приедет.

Отсюда практическое следствие, из-за которого и заводятся пакеты: **всё, без
чего требование неверно, лежит в том же файле или в том же пакете.** Ссылка
годится для «а вот смежная тема», не для «а недостающая половина правила там».

## Скилл сам в работу не приходит

Правило действует, только когда загружено. Поэтому условия загрузки
перечисляются в файле контекста проекта — по всем скиллам, а не по избранным
(`docs-context-files`).

Скилл, о существовании которого написано, но не написано, когда его открывать,
не действует. Это не гипотеза: именно так и выглядит большинство «правил,
которые почему-то не соблюдаются».

## Развилки закрывает проект

Универсальное правило вынуждено называть обе ветки: «`asChild` в Radix или
`render` в Base UI», «в монорепозитории так, в одиночном репозитории иначе».
Читателю в конкретном проекте нужна одна.

Поэтому выбор пришпиливается в файле контекста проекта, и это не дублирование,
а единственное место с гарантированной загрузкой: файл контекста читается
целиком каждую сессию, а скилл — по условию.

Обратное тоже верно: **адаптация универсального скилла под проект пишется в
файле контекста или в разделе отступлений проектной копии, а не правкой тела
скилла.** Правку тела съест следующее обновление из библиотеки.

## Имя

Каноническое имя — `<область>-<имя>`, и оно же становится именем каталога при
переносе в проект. Под ним правила ссылаются друг на друга.

Переименование при адаптации ломает перекрытие личным скиллом
([placement.md](placement.md)) — это его главное практическое последствие,
и о нём легко забыть.

## Проверка

- назвать три реальные ситуации, в которых правило нужно, — все три следуют
  из описания;
- назвать ситуацию, где правило не нужно, и проверить, что описание её не
  захватывает;
- прочитать правило, не открывая ничего по ссылкам, — оно остаётся верным и
  применимым;
- найти в файле контекста проекта строку про условия загрузки этого правила —
  она есть.

## Чего не делать

- писать описание для человека, а не для срабатывания;
- выносить необходимую часть правила за ссылку;
- рассчитывать, что скилл подхватится сам, без записи в файле контекста;
- править тело перенесённого скилла вместо записи отступления.

## Смежное

- [placement.md](placement.md) — где правило живёт и что перекрывает что.
- [package.md](package.md) — почему одна точка входа лучше сорока.
