# Реализация и дисциплина проверок

## Реализация

- **Реальный код** (логика бэкенда и фронтенда) — TDD: сначала тесты, убедиться,
  что падают по правильной причине, потом реализация, пока тесты не
  позеленеют по-настоящему — реальным прогоном командой из проекта, не на
  словах. Один агент видит и тесты, и реализацию; будьте самокритичны.
- **Документация, конфиги, скиллы** — без тестов и без суррогатных
  grep-проверок под видом тестов. Критерий «готово» — построчная сверка
  результата с планом, обычное чтение.
- Зависимости и окружение — только так, как документировано в README
  проекта, без импровизированных docker-флагов и env. Если документированный
  способ не работает — зафиксировать точную ошибку и вероятную первопричину и
  сказать вслух, не изобретать обходной путь молча.
- Коммитить по ходу, не всё одним махом в конце. Сообщения в стиле
  репозитория: коротко, на русском, по смыслу изменения.
- **Push — только по явному разрешению** пользователя.

## Дисциплина проверок

Правило: **в рабочем цикле — только быстрые проверки; тяжёлые — один раз на
блок задач.** Ориентир — прогон в цикле не дольше ~30 секунд.

- Быстрые: проверка типов, линт, юнит-тесты без БД, целевой файл тестов. В
  питон-проектах — маркер вроде `-m "not db"` или готовый скрипт быстрых
  тестов, если он в репозитории есть.
- Тяжёлые: сьюты на реальной БД, тесты с настоящими интеграциями и фикстурами
  внешних API. Запускать, только если нужны именно эти данные, и один раз в
  конце смыслового блока задач.
- Задачи, которые проверяются одним и тем же тяжёлым сьютом, **объединять** и
  прогонять его после них один раз, а не после каждой.

Почему это правило, а не пожелание. Тяжёлый сьют, прогоняемый после каждого
шага по 6–7 минут, даёт часы ожидания и, что хуже, искажает калибровку: полки
сторипоинтов, снятые с такой сессии, завышены привычкой, а не работой. Плохая
дисциплина проверок не только замедляет работу, но и портит данные, по
которым оценивается будущая.

Отдельно: «зелёные тесты» всё равно означают реальный прогон, а не
рассуждение. Правило про быстрые проверки — про то, ЧТО гонять в цикле, а не
про право не гонять ничего.

## Проверка

- прогнать тесты проекта настоящей командой — зелёные, а не «должны быть»;
- засечь прогон, который идёт в рабочем цикле, — укладывается примерно в
  полминуты;
- посмотреть историю коммитов истории — их несколько по завершённой логике, а
  не один в конце.

## Чего не делать

- гонять тяжёлый набор тестов после каждого шага;
- объявлять тесты зелёными без прогона;
- изобретать обходной способ поднять окружение вместо документированного;
- пушить без явного разрешения.
