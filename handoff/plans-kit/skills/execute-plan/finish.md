# Завершение плана

## Порядок завершения

Реально прогнать тестовый сьют проекта (команды из README или `AGENTS.md`) —
идти дальше только когда зелёные. Для документационной задачи — план выполнен
построчно.

Смёрджить ветку задачи в `base_branch`:

```bash
git checkout <base_branch>
git merge --no-ff <ветка задачи>
```

Тривиальный конфликт (форматирование, соседние строки) — разрешить самой,
сохранив полезные изменения обеих сторон. Смысловой конфликт (обе стороны
по-разному меняют одну логику) — `merge --abort`, объяснить и дождаться
решения пользователя, не придумывать его самой.

После мёрджа проверить, что ветка не разошлась:

```bash
git diff --exit-code <base_branch> <ветка задачи>
```

Пусто (`exit=0`) — удалить ветку (`git branch -d`). Не пусто — не удалять
ничего, объяснить расхождение. Обновить frontmatter плана: `status: merged`,
дописать в журнал итог.

## Если застряли

Не тянуть тихо и не перебирать попытки в одиночку — сказать пользователю
прямо, что не получается и почему.

Это про **настоящий тупик**, а не про паузу после каждой истории: если работу
можно продолжить, приняв разумное допущение, она продолжается, а вопрос уходит
в файл открытых вопросов (см. [continuity.md](continuity.md)).

## Проверка

- `git diff --exit-code <base_branch> <ветка задачи>` пусто — только тогда
  ветка удаляется;
- во frontmatter плана `status: merged` и итоговая запись в журнале.

## Чего не делать

- удалять ветку, не убедившись, что она не разошлась;
- разрешать смысловой конфликт слияния за человека;
- тянуть тупик молча вместо того, чтобы сказать о нём.
